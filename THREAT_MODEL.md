# VSA website threat model

**Scope:** Production VSA website and its Supabase, Vercel and GitHub workflow boundaries. This is a public repository; never put credentials, private student data, attack instructions or actual check-in values here.

Review this document when adding a new feature or changing a trust boundary, **in the same PR**. Mark a control **unverified** unless a focused test or deployed verification proves it. Browser checks and client validation are UX, not authorization.

| Feature / trust boundary: what are we doing? | What could go wrong? | Control: how is it addressed? | Evidence: how do we know? |
| --- | --- | --- | --- |
| Public points lookup and leaderboard, using member-based standings | Private fields leak; rankings drift from the attendance ledger | Public projections and read-only repositories, with restricted column access; canonical model described in [leaderboard system](docs/leaderboard-system.md) | `src/data/repos/leaderboard.test.ts`, `src/data/repos/leaderboardViews.migration.test.ts`; live privilege checks: [RLS checklist](docs/rls-verification-checklist.md) |
| Former member accounts and code-based check-in | Retired APIs regain write permissions or mistaken identity changes points | Member-account retirement contract and restricted legacy functionality; do **not** reactivate when adding a new feature | `src/__meta__/memberAccountRetirement.test.ts`; [retirement runbook](docs/member-account-retirement.md); production permissions need the phase-aware [RLS verifier](docs/rls-verification-checklist.md) |
| Admin routes, Auth and database actions | A browser route guard is mistaken for server authorization | `src/routes/AdminRoute.tsx` is presentation only; RLS, service-side authorization and scoped database privileges enforce access | [Auth model](docs/auth-model.md), `src/routes/AdminRoute.test.tsx`; server proof requires `scripts/verify-rls-security.mjs` |
| Ask VSA assistant and its paid model calls | Disclosure of private facts, prompt manipulation, runaway usage | `supabase/functions/vsa-ai-assistant/index.ts` contains refusal logic, grounded retrieval and usage limits; service secrets stay server-side | `supabase/functions/vsa-ai-assistant/` tests and [AI knowledge freshness tests](src/lib/aiKnowledgeFreshness.test.ts); ongoing cost verification: [#240](https://github.com/hhavynn/vsa-website/issues/240) |
| Image-migration dispatch Edge Functions | Unauthorized workflow dispatch or unbounded external CI cost | `supabase/functions/trigger-event-image-migration/` and `trigger-house-event-image-migration/` enforce server authorization and request ceilings | `scripts/test-privileged-edge-quotas.sh` (offline), hosted checks **unverified** here; [#352](https://github.com/hhavynn/vsa-website/issues/352) |
| Application forms and recruitment windows | Closed/future application links leak via public HTML or APIs | `src/data/repos/applicationLinks.ts` reads a public masked projection; admin-managed windows set visibility | `src/data/repos/applicationLinks.test.ts`, `src/lib/applicationWindowBoundaries.test.ts`; manual timing/deploy QA is separate |
| Data-rights requests and member photo requests | Personally identifiable information is disclosed or photos published without consent | Consent validation, private request workflows and approved public-photo paths; server checks must remain authoritative | `src/schemas/memberPhotoRequests.test.ts`, `src/data/repos/photoRequests.submit.test.ts`; [data-rights runbook](docs/data-rights-anonymization-runbook.md) and [RLS checklist](docs/rls-verification-checklist.md) |
| Supabase Storage and public images | Private uploads become public or bandwidth costs spike | Scoped Storage rules, upload brokers and public-image migration architecture; never delete original Storage objects automatically | `src/lib/imageDelivery.test.ts`, `src/__meta__/storageAuditScript.test.ts`; current live cost **unverified** without the [Storage audit](docs/event-image-migration.md) |
| Public feedback submissions | Caller spoofs account attribution or floods inserts | `submit-feedback` Edge Function derives verified identity and invokes a bounded service-only RPC; direct browser inserts cut off in ordered rollout | `scripts/test-feedback-boundary.sh` and [rollout status](docs/feedback-submission-rollout.md); hosted permissions must be separately checked |
| Deploy pipeline and public environment config | Secrets bundled into client JS or unreviewed changes reach production | Public-only `REACT_APP_*` convention, PR security checks, deploy workflow; GitHub branch protection is an independent setting | `.github/workflows/deploy.yml`; proposed client-secret tripwire [#348](https://github.com/hhavynn/vsa-website/issues/348), branch-protection evidence **unverified**: [#357](https://github.com/hhavynn/vsa-website/issues/357) |

## Reviewer check

For each new or changed trust boundary, answer: what is the purpose; what could fail; what server-side control actually exists; which test or hosted check proves it? Record missing proof as **unverified** and link a follow-up issue. Do not call an offline mock test evidence of hosted RLS or production configuration.

For deeper security history and decisions, consult [Auth model](docs/auth-model.md), [RLS verification checklist](docs/rls-verification-checklist.md) and [failure archaeology](.claude/skills/vsa-failure-archaeology/SKILL.md). Avoid reproducing sensitive operational detail from those sources here.
